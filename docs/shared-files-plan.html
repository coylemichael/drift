Shared files under many agents

Drift plan · drafted 2026-10-09 · status: built in 999390e, 6c3e773, 96bab20, d8c7964 (v0.5.0)

Amended 2026-10-10: §5's edit-back rule (a bullet edited in CHANGELOG.md written back to its fragment) proved destructive in use and was removed in 2097285 — generation is one-way, and a hand-edited bullet is reported and refused. This document records the design as built; current behaviour is described in README.md.

When a dozen agents land on one branch within minutes of each other, the files every one of them touches, drift/INDEX.md and CHANGELOG.md, conflict on nearly every rebase, and the hand resolutions silently lose work. This plan makes both files derived: rebuilt from per-thread source files that cannot collide, merged by code when two versions meet, and never resolved by a model or a person. A third piece, /drift-land, turns the landing rulebook into one command.

1. What went wrong

Observed in perimeter, 5–8 October 2026, with 8–12 coordinated threads landing hourly:

  • Every rebase conflicted on CHANGELOG.md (two sections inserted at the top of [Unreleased]) and drift/INDEX.md (two rows appended, both numbered last + 1, footer count changed).
  • Resolutions lost work silently. A "keep mine" resolution erased the other thread's entry with no test failing (Ashguard's tier-2 entry, knocked off main twice in four hours). A reverse patch replaced the Hook's entry instead of keeping both (c05327c6).
  • Hand edits corrupted the index: duplicate # numbers, rows above the header (c955acdc), a stale footer.
  • The landing race did the worst damage: a git reset --soft origin/main after origin/main had moved reverted three other threads' landings, twenty files (e6f4938b, repaired in d8b3b8c0).
  • At release, 27 per-thread changelog sections had to be collapsed by hand (drift/programme/148).

The rules written afterwards ("insert only your own hunk", "keep both sides", "git diff origin/main --stat must list only your files") are correct and were followed most of the time. Discipline is not the fix; the file layout is.

2. The principle

A shared file is either append-only-by-unique-name or derived. Large projects never let N writers edit one changelog in flight: CPython (Misc/NEWS.d/), Twisted and pip (towncrier), JS monorepos (changesets) and GitLab all write one new, uniquely named file per change and generate the human file from them. Kubernetes and Rust harvest release notes from the PR itself. The Linux kernel has no changelog file at all.

Drift already applies this to the index: artifacts are the source, INDEX.md is a view rebuilt from their frontmatter. What was missing is (a) a way for two committed views to meet without a textual conflict, and (b) the same treatment for the changelog.

Git's purpose-built hook for "both sides changed this file" is the merge driver: a per-file program named in .gitattributes that runs during every merge, rebase, cherry-pick and stash pop, receives base/ours/theirs, and writes the result. A prototype row-level driver for INDEX.md was run through a rebase and a merge of two threads that each appended row 003: both completed with no stop and no markers, four rows ordered by true timestamp (the 11:30 row ahead of the 12:00 one that landed first), renumbered, footer recounted. With the driver undefined, git falls back silently to a normal text merge, so the attribute is safe to commit anywhere.

3. Scope and requirements

Drift-only
The self-merging index and changelog work in clones where Drift is installed and has configured the driver. Merges done on a web UI or in a bare clone get a plain git conflict; that is outside what Drift supports, and is stated as such.
Never lose a fragment, never guess
Fragments (artifacts, changelog entries) are the source and are never deleted by Drift. Anything Drift cannot interpret is carried through unchanged and reported, never dropped or repaired by inference. This matches how Drift already treats malformed .drift.json and ignore-rule conflicts.
Deterministic
Every derived file is a pure function of the set of source files, ordered by true timestamp with the id as tie-break, so two worktrees compute identical text from identical inputs. That is the property the merge driver depends on.
No new manual steps
Threads keep doing what they do today: publish, commit, fetch, rebase, push. The steps that disappear are the conflict resolution, renumbering, footer recount and diff check.
Out of scope
Cross-machine clock skew (seconds, cosmetic; Drift already refuses estimated timestamps). Agents that write to the generated region in a format Drift does not define (see §5.5). Serialising landings across machines (a merge queue is a project concern).

4. Piece A: the self-merging index

The index is kept accurate in every mode, and worktrees always come back together. It is rebuilt from the artifacts on disk at publish, at session start and inside /drift-land, whether or not it is ever committed. Each mode has its own consolidation point: in tracked mode artifacts travel through commits and git merges them at the rebase (§4.1–4.3); in private mode git carries nothing, so every worktree of a repo shares one local store from the start (§4.5). The changelog (§5) is a repo file whether or not drift/ is tracked, so /drift-changelog on stands alone and does not consult the tracking flag.

4.1 build-index.py --merge O A B

A new mode of the existing stdlib renderer, usable as a git merge driver. It merges rows, not trees: during a merge the other side's artifact files may not be in the working tree yet, and a row already carries everything needed (date, feature, type, path).

  • Union of rows keyed by artifact path. A row present in base and removed on exactly one side is removed; removed on both, removed.
  • Sort by UTC-normalised instant, then feature, then folder sequence. Renumber # from 001. Recount the footer. Header prose taken from A. ## Undated entries unioned the same way.
  • Same id with different text on both sides: take B's; the next frontmatter rebuild is authoritative.
  • Writes the result to A and exits 0. Exit 1 only when input is not a Drift index at all.

4.2 The attribute and the driver tracked mode

  • /drift-track-artifacts on also writes drift/INDEX.md merge=drift-index to .gitattributes (the index is only committed in tracked mode). The line is left in place on off; it is inert without the driver.
  • At session start, when the repo is tracked and the attribute is present, the Pi extension installs the driver in that clone's .git/config: merge.drift-index.name and merge.drift-index.driver = <python> -I <checkout>/scripts/build-index.py --merge %O %A %B. Paths use forward slashes (git runs drivers through sh -c, which eats backslashes on Windows). DRIFT_PYTHON is respected. Already-correct config is left alone; a different existing value is reported, not overwritten.
  • hosts/claude.md and the skill carry the same one-line git config for hosts without the extension.

4.3 Remote-aware numbering tracked mode

In tracked mode the next NNN for a feature is the maximum over the working folder and git ls-tree of every remote-tracking ref for drift/<feature>/ (no network; whatever the last fetch saw), plus one. Two threads can still mint the same number before either pushes; the result is two differently named files, untidy but not a collision. Identical feature, number and slug is an add/add conflict git reports loudly.

4.4 Session-start sync guard

The existing index rebuild at session start skips when .git/rebase-merge, .git/rebase-apply or .git/MERGE_HEAD exists, so it never writes over a merge in progress.

4.5 One private store per repo private mode built

Today an ignored drift/ is per worktree: a rebase onto main brings over no artifacts, because none were ever committed, and removing a finished worktree deletes its handoffs. In private mode the worktrees therefore share one store from the start, so there is nothing to consolidate later.

  • The main worktree's drift/ is the store for the whole repo on that machine. Drift locates it from git rev-parse --git-common-dir, which every worktree shares.
  • A linked worktree holds no drift/ at all. Drift resolves the store in code (artifactStore()) for publication, the index, /drift pick-up, drift-continue and the session context, which states where the artifacts live. The artifact records the worktree's own branch and commit.
  • Consequences: one index per repo per machine, accurate across every thread; /drift sees every handoff; one publish lock and one NNN sequence across worktrees, so duplicate numbers cannot arise in private mode; removing a worktree removes nothing of Drift's.
  • Tracked mode is unchanged: artifacts stay in each worktree so they commit with the branch, and git is the consolidation point.
  • A private worktree that already holds its own artifacts keeps using them and is reported ("two stores"); Drift moves nothing.
  • Locating the store: the drift/ at the main worktree's root, found from the common dir. Drift never creates anything outside a project root: when there is no main worktree, as with a bare repository plus linked worktrees, each worktree keeps its own drift/ as today and the session context says so. Decided 2026-10-09.

Why not a junction. The first build linked the worktree's drift/ to the store. Measured 2026-10-09 with Git for Windows 2.52: git treats a junction as an ordinary directory, so a plain git worktree remove (no --force needed) descended through it and deleted the store's artifacts and index. True directory symlinks need Developer Mode on Windows (EPERM otherwise). Links were therefore dropped; the regression test now asserts the store survives worktree removal.

5. Piece B: the derived changelog

5.1 Trigger

Automatic with an origin remote (decided 2026-10-09, replacing an opt-in command). Nothing in this piece matters until two copies of the file can meet in git, which needs a shared branch; so in a repository with an origin and a root CHANGELOG.md, the first session start or publication adopts the file with no command, and a local-only repository has one writer and is left alone. .drift.json overrides either way: "changelog": false keeps a shared repo's changelog hand-written, true forces a local one; /drift-changelog on|off|status sets or explains it. The same trigger writes the tracked index's attribute (§4.2). Adoption creates changelog.d/README.md (the convention in one paragraph, for any agent that reads the repo); inserts the marker line at the top of CHANGELOG.md, creating the file if absent, so everything already there becomes the preserved history below it; adds CHANGELOG.md merge=drift-changelog to .gitattributes. Off: flips the flag; files are left in place. Nothing is staged or committed. When a repo has a root CHANGELOG.md and the flag is unset, session context carries a one-line hint once.

If the repo already uses towncrier, changesets or a newsfragments/ directory, on refuses and names it: follow the repo's own convention instead.

5.2 Fragments

changelog.d/cards-pass-043-ledger-recut.md
---
date: "2026-10-09T16:29:21+01:00"
section: "Changed"
artifact: "drift/cards-pass/043-handoff-ledger-recut.md"
---
**The Marksman's Ledger's cards re-cut to impress.** Culling draws its line …
  • Named <feature>-<NNN>-<slug>.md after the artifact, so names are unique by construction. Committed with the code; not under the ignored drift/.
  • section is one of Keep a Changelog's types (Added, Changed, Deprecated, Removed, Fixed, Security). date is the artifact's measured date. The body is the bullet, Markdown allowed.
  • Written by drift_publish when the optional changelog: { section, text } input is supplied, alongside the artifact, under the publish lock. An agent without the tool writes the file by hand; the skill's rule is "write a fragment, never edit the changelog".
  • Fragments are never deleted or moved by Drift. Versions are derived, not stamped (decided 2026-10-09, replacing an earlier stamp command): a release is already recorded in the repository as a version tag (vX.Y.Z by default, pattern configurable), so a fragment belongs to the first version tag whose tree contains it (git ls-tree <tag> -- changelog.d/). Membership comes from git ancestry, never timestamps, so it is exact and identical in every worktree; a clone that has not fetched the new tag shows those entries as unreleased until it does. Projects without version tags keep day grouping. Nothing to type at release time.

5.3 Generation

scripts/build-changelog.py <repo> [--stdout | --check | --merge O A B], stdlib only, the same shape as the index builder.

  • Owns only the region above the marker <!-- drift:changelog — generated from changelog.d/. Edit a bullet if you keep its id comment. -->. Below it, the repo's hand-written history is untouched.
  • Newest first, grouped by version tag (## [0.7.3] — date of the tagged commit) when the repository has version tags, with fragments in no tag under ## [Unreleased]; otherwise by day (## 2026-10-09). Then by section (### Changed). Within a group, newest first, id as tie-break.
  • Each bullet ends with its id as an HTML comment: … <!-- changelog.d/cards-pass-043-ledger-recut.md -->. Invisible when rendered; the key for merging and edit-back.
  • Written with compare-and-swap: hash on read, re-check immediately before the atomic replace, re-read and retry if another process wrote in between. The window shrinks to the rename itself.

5.5 Hand edits

  • Editing a bullet's text is supported if its id comment stays. On the next regeneration Drift sees text that differs from the fragment and writes the edit back into the fragment, so it persists. Keyed by id; no inference.
  • A bullet without an id is unsupported. Drift never deletes it: the driver carries such lines through verbatim at the top of the generated region, and regeneration reports "unrecognised entries at lines N; move them into a fragment or delete them" and skips the changelog step for that run. Drift is an automation tool; it does not guess at a format it did not write.

5.6 The driver

--merge O A B: parse both generated regions into entries keyed by id; union with the same base-deletion rule as the index; same id with different text, take B's (the fragment is authoritative on the next rebuild); carry un-id'd lines through; regenerate the region. Below the marker, run an ordinary three-way merge (git merge-file semantics); a genuine conflict there exits 1 and surfaces normally. Installed per clone at session start exactly like the index driver, under merge.drift-changelog, whenever .drift.json has "changelog": true and the attribute is present; tracking mode is not consulted.

6. Life of a change, twelve threads at once

  1. Thread 7 records a change. Its handoff publication writes changelog.d/cards-pass-043-ledger-recut.md. Twelve threads, twelve files, twelve different names.
  2. The same publish regenerates CHANGELOG.md locally from every fragment in that worktree (main's as of the branch point, plus its own), and rebuilds the index. Thread 7's commit carries derived files correct for what it can see.
  3. Thread 7 lands: fetch, rebase, push. If nothing landed meanwhile, the rebase is clean and the push goes through. If thread 3 landed a fragment an hour ago, the rebase hits CHANGELOG.md and INDEX.md; the drivers union the entries, reorder by timestamp, regroup, and the rebase continues without stopping. The push carries both threads' entries in the right order, with neither thread having read the other's text.
  4. main is always current. After every landing, main's derived files equal "compile every fragment on main". Twelve landings in any order each fold in what arrived before them. There is no batch step.
  5. Correction passes catch what slips. A fragment written by hand in a thread that never regenerated is absent from main's changelog only until the next regeneration anywhere: any publish, any session start. Staleness, not loss.

In a shared checkout (several threads in one clone, as on 5 October) there is no merge at all: every publish regenerates from all fragments on disk under one lock, and threads commit their own files by path.

8. Piece C: landing, automatic at the interval boundary

Drift already knows when a unit of work ends: the handoff that completes the interval. With a one-time repo opt-in, that handoff lands itself, and the profiled continuation then starts from landed main. /drift-land is the same sequence as a manual command for an ad-hoc push. Either way, the sequence that caused e6f4938b cannot be typed. Decided 2026-10-09 (replacing a manual-only command).

{ "land": { "auto": true, "check": "pytest -q" } }
{ "land": { "auto": true, "check": ["cargo fmt --check", "cargo test"] } }

Order in the automatic chain: publish handoff → land → compaction → drift-continue. A real conflict in a non-derived file, or the guard tripping, halts the chain there: the handoff stays published, the record is checkpointed, and the thread reports exactly what blocked. That is the same rule Drift applies to a pending user decision. Pushing is the one outward-facing act in this plan, so it follows the trackArtifacts pattern: one explicit line per repository, never inferred.

  1. Preconditions: on a branch, tree clean apart from Drift's own regenerated files, no merge in progress. A completed handoff with uncommitted changes is reported, not committed: what goes into a commit is the agent's judgement, landing is mechanical.
  2. Take a cross-worktree lock under git rev-parse --git-common-dir (worktrees share it).
  3. git fetch; rebase onto origin/<default>. The drivers resolve the index and changelog; any other conflict stops the command with the file named.
  4. Regenerate index and changelog; --check both.
  5. Guard: git diff origin/<default> --name-only must equal the files touched by git log origin/<default>..HEAD. Anything else listed means a landing went wrong; stop and show it.
  6. Run the repo's configured check: any shell command or list of commands, run in the worktree through the platform shell, in order, stopping at the first non-zero exit, whose output is the failure report. Unset means nothing runs and the landing report says "no check configured"; Drift may suggest a line from what it sees (package.json, pyproject.toml, Cargo.toml, Makefile) but never runs one unasked. Nothing in this plan assumes a toolchain in the target repository; Node is only Drift's own runtime.
  7. git push origin HEAD:<default>. On rejection (someone pushed between fetch and push), loop from step 3, bounded.
  8. Checkpoint the record with reason land, so the interval shows when its commits were rebased and pushed.

It never squashes, never force-pushes, never resets against a moving ref. Squashing stays a deliberate, separate act done before landing, against a named commit.

10. Decisions and open questions

Decided
Derived changelog, not compile-at-release: most projects do not release, and a running log is the common case. Row/entry merging in the driver rather than tree rebuild. Opt-in via command, as with tracking. Keep a Changelog section vocabulary. Day grouping by default. Fragments live at repo root in changelog.d/, committed. Drift-only support.
Decided later the same day
No stamp: versions derive from tags. Landing is automatic after a completed handoff when the repo opts in, with the manual command as its ad-hoc form. The check command is any shell command, unset runs nothing and says so.
Open
Whether the un-id'd-entry report should also appear in Pi's session context so a thread sees it before publishing. The default tag pattern (v*) and whether the section date is the tagged commit's date or the tag's own date for annotated tags.

Not in this plan. Serialising landings across machines (a merge queue), changing tracked-mode defaults, and making ROADMAP.md derived. The roadmap is a living document with an owner, not an append-only log; it needs the coordinator, not a compiler.
