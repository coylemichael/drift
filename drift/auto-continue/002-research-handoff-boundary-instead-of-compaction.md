## Research Question

Drift's automatic continuation was meant to start each next task from the handoff alone ("we don't need compaction because we have handovers"). Observed in the Rig repository, every automatic continuation instead carried a Pi compaction summary plus a large retained tail of the previous transcript. How does the current mechanism work, why does it carry old context, and what Pi primitives allow a handoff-only boundary?

## Summary

On `agent_settled` the extension calls Pi's ordinary `ctx.compact()` with custom instructions only. That runs Pi's default LLM summarization (uncached, 43k–171k input tokens per handoff in Rig, 35–82 s) and keeps Pi's default recent tail (`keepRecentTokens`, default 20k by estimate; 27–40k tokens measured), so each "fresh" window starts at ~45–57k tokens, mostly the previous interval's tool output. Pi 0.87.0+ (Drift's dev floor is ^1.1.0; installed 1.2.0) provides an `agent_before_settle` boundary that can append a **retain-none compaction draft** (`firstKeptEntryId: null`) with an extension-supplied summary and no LLM call, which gives a handoff-only boundary in the same Pi session. Session replacement (`newSession`) also exists but is command-context only and changes session identity.

## Detailed Findings

### Current continuation chain (Drift extension, commit 5e09cf1)

- `drift_publish` decides whether to queue: a profiled, non-complete, non-held handoff in a repo with `autoContinue: true` sets `pendingContinuationPath` and reports "A fresh profiled context window is queued automatically." (`extensions/drift.ts:586-594`).
- In-memory state: `pendingContinuationPath` / `continuationQueued` (`extensions/drift.ts:41-42`), reset when the cwd/session identity changes (`extensions/drift.ts:61-64`).
- `agent_settled` handler (`extensions/drift.ts:483-505`): checkpoints, then if a path is pending and not yet queued, sets `continuationQueued` and calls `ctx.compact({ customInstructions: "A Drift handoff was published at … Preserve only the minimal continuation context; the next turn will read the handoff and its referenced artifacts directly.", onComplete, onError })`. `onComplete` sends `drift-continue <artifact>` with `pi.sendUserMessage`; `onError` clears the queue and notifies.
- The bare `drift-continue` input handler (`extensions/drift.ts:386-393`) calls `continueHandoff` (`extensions/drift.ts:252-284`): reads the handoff route, loads the profile map (`lib/routing.ts:71-74`), `pi.setModel` + `setThinkingLevel` **before** inference, clears the queue, then sends the "Continue the work recorded in the Drift handoff at …" user message (plus citation note).
- `session_before_compact` and `session_before_tree` are guarded by `guardSummary` (`extensions/drift.ts:470-481`), which cancels summaries when the Drift record failed.
- User-facing wording that describes the mechanism as compaction: `extensions/drift.ts:350` (command description), `extensions/drift.ts:539` (promptGuidelines), `extensions/drift.ts:489,574` (comments), `lib/state.ts:180,247,253` (config doc/status text), `README.md:67,208`, `docs/continuation.md:18`, `skills/drift/hosts/pi.md:39` ("After compaction, Pi uses `drift-continue` internally …").

### What `ctx.compact()` does in Pi (installed Pi 1.2.0)

- `CompactOptions` accepts only `customInstructions`, `onComplete`, `onError`; there is no retain/keep option (`dist/core/extensions/types.d.ts:204-208`).
- Default compaction walks back to `keepRecentTokens` (default 20000, settings-level only), LLM-summarizes everything before the cut with Pi's structured format, and rebuilds context as summary + entries from `firstKeptEntryId` (Pi `docs/compaction.md`, "How It Works" and "Settings"). Summarization requests disable prompt-cache writes.

### Pi primitives for a handoff-only boundary

- **Actionable boundaries (Pi ≥ 0.87.0, CHANGELOG lines 448-449).** `turn_end` and `agent_before_settle` handlers may return `{ entries: [...drafts], continue? }`. Drafts include `CompactionEntryDraft { type: "compaction"; summary; firstKeptEntryId: string | null; details?; usage? }`; `null` "creates a self-retaining compaction that keeps no preceding entries" (`dist/core/extensions/types.d.ts:768-775`, Pi `docs/session-format.md:131`, `docs/compaction.md` "retain-none").
- Implementation: `_runBeforeSettleBoundary` emits `agent_before_settle`, commits drafts, then continues only if `result.continue` or queued messages exist (`dist/core/agent-session.js:1536-1558`). `_applyBoundaryDrafts` appends a compaction draft via `sessionManager.appendCompaction(summary, firstKeptEntryId, tokensBefore, details, fromHook=true, usage)` — **no LLM call, no `session_before_compact`** (`dist/core/agent-session.js:579-604`). `appendCompaction` stores `firstKeptEntryId ?? id` (`dist/core/session-manager.js:880-898`).
- Context after such an entry: system prompt + the compaction summary rendered as a `compactionSummary` message ("The conversation history before this point was compacted into the following summary: …", `dist/core/messages.js:7,103-107`) + anything appended after it.
- `agent_before_settle` sees `event.context.pendingMessages` (queued user messages). With queued messages the run continues instead of settling (`agent-session.js:1547`), i.e. a boundary appended then would put the queued user message into the empty context.
- `agent_settled` is notification-only and fires once nothing else will run; `prompt()`/`sendUserMessage` during it is deferred until after settlement (`agent-session.js:1602-1605`), which is how the current `drift-continue` dispatch works.
- **Session replacement.** `ExtensionCommandContext.newSession/fork/switchSession` exist but are command-only "because calling them from lifecycle handlers can deadlock the runtime" (Pi `docs/extensions.md`, "Context and session changes"; `types.d.ts:287-323`). `drift-continue` is an `input` handler, not a command; Drift records, intercom identity and the `store()` key are all per Pi session ID (`extensions/drift.ts:52-64`).

## Options (requested by the user)

1. **Retain-none handoff boundary at `agent_before_settle` (same Pi session).** When a continuation is pending and no user messages are queued, return a compaction draft with `firstKeptEntryId: null` and a deterministic summary naming the handoff; then on `agent_settled` send `drift-continue <artifact>` as today. No summarizer call, no retained tail; the next window is system prompt + one short boundary note + the continuation prompt. Keeps the Pi session ID, Drift record, intercom identity and existing `drift-continue` model selection. Raw history stays in the session file.
2. **New Pi session per handoff.** Truly separate thread, but requires command context (deadlock risk from lifecycle handlers), changes session ID/record/intercom identity per hop, and needs a new dispatch path for automatic continuation.
3. **Keep `ctx.compact` but shrink the tail.** Not possible per call (`CompactOptions` has no keep option); `keepRecentTokens` is a user/project setting and still leaves an LLM summary.

## Open Questions

- Should a manual `drift-continue` typed into a thread with prior conversation also start a handoff-only boundary? There is no boundary event before the first request of a new run; the existing guidance is "run it in a fresh thread".
- Should an aborted run (Escape) after a successful handoff publication still continue automatically? Current `agent_settled` code ignores `aborted`.
