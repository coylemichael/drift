# Drift on Pi

This overlay applies when the `drift_publish` tool is available. It says only what it replaces in the core skill; everything else in `SKILL.md`, `research.md`, `plan.md`, `execute.md` and `handoff.md` still applies.

## Bundled workflow binding

The Pi extension binds Drift's advertised skill and explicit `/skill:drift` requests to the skill shipped alongside that extension. A stale standalone copy may still appear in Pi's discovery inventory, but it does not supply the runtime workflow. Do not delete old skill checkouts or edit user settings to resolve that collision. Other skills and explicitly disabled discovery are preserved.

## Drift root and worktree adoption

The **Drift root** is the checkout Drift operates on: the session's launch repository, or the worktree adopted with `drift_worktree`. Read it from session context or `drift_worktree { action: "status" }`. Everything this overlay calls "the repository" — `.drift.json`, `drift/`, numbering, refs, continuation artifacts — means the Drift root. In a private-mode linked worktree the artifact store is the main worktree's `drift/`, but policy and metadata still come from the Drift root.

If you are a worker assigned a worktree, adopt it **before substantive work**: call `drift_worktree { action: "adopt", path: "<worktree root>" }` as the **only** call in its tool-call batch (no parallel publication, shell or edits). It fails while a publication is pending or a continuation is queued. The target must be an existing exact worktree root of the same repository; Drift does not create, rebase or repair worktrees or policy. The ordinary session-start preparation runs before the new baseline. Adoption starts a fresh measured baseline and keeps earlier baselines/receipts in the record history; it does not write a handoff, complete an interval, or measure work done before it. The binding persists across reload, resume, compaction and continuation of this session only. An orchestrator may stay in the main checkout.

Adoption does not change Pi's `cwd`, built-in tool defaults, session-file location or trust. Pass absolute worker paths to `read`, `edit` and `bash`; `cd` alone does not move Drift. The adopted checkout's `.pi/drift-model-profiles.json` is not trusted by adoption; the global profile map applies. If `drift_worktree` is absent, the running extension predates it; ask the user to `/reload` or reconnect.

**Blocker rule.** Verify the intended Drift root once. If it is wrong (unadopted, wrong worktree, removed target) or the policy check fails, report once that publication is blocked and why. Do not hand-write a managed artifact, `.drift.json` or session record to get around it. Continue investigation that does not depend on publication, and recheck only after a relevant change or when the user asks. A removed or recreated target fails explicitly with no fallback; `status`/`adopt` remain available to recover with a fresh baseline. If a queued continuation stalls, status names the `/drift <handoff>` command that picks it up on the selected model; reloading clears that in-memory queue without deleting the artifact.

## `/drift`

`/drift` is the user's entry point on Pi. The extension chooses the artifact in code before the turn reaches you, then hands you an ordinary Drift skill request: with nothing named, the newest artifact queried from the raw Markdown files through the shared parser, routed by the pick-up rule in `SKILL.md`; with a link, path or file name, that artifact plus the user's words; with anything else, the request as typed. `/drift` always runs on the model the user currently has selected; it never switches models or profiles. Trust the named path in that request and do not re-pick. Pickup and the bounded recent-artifact context read the raw artifacts directly; raw discovery failures are reported, with no fallback.

## Publishing with `drift_publish`

Use `drift_publish` to save research, plan and handoff artifacts. First read the relevant workflow file and write its required Markdown sections. Pass the confirmed feature, artifact kind, a safe lowercase slug, the body **without frontmatter**, and any source/previous/related artifact paths. References are repository-relative `drift/...` paths.

The tool owns the measured frontmatter, sequence allocation, artifact Git-policy enforcement, artifact writes and handoff completion. It reads the Drift root's `.drift.json` on every publication: `trackArtifacts: true` leaves ignores untouched and requires trackable artifact paths; missing/false retains the ignored default. It never stages or commits. Do not duplicate those writes or delete session records yourself. To switch a repo between tracked and ignored artifacts, the user runs `/drift-track-artifacts [on|off|status]`; it is a user command handled by the extension, so suggest it rather than writing `.drift.json` yourself. The publisher writes no index or changelog file. New publisher snapshots also record deterministic `anchor_coverage` even with zero eligible numeric citations; skipped reasons/counts are bounded and capture completeness is not freshness. Symbol-only references remain valid. Reload to activate a changed publisher; legacy artifacts and pending intents are not backfilled. Optional source/previous references may be omitted or blank; use `[]` when there are no related artifacts. Correct argument validation errors before retrying. Once a pending publication exists, keep the record and retry the **same input**; report conflicts instead of deleting partial work.

The publisher writes the artifact's initial `status` (see "Artifact Status" in `SKILL.md`): research `complete`, plan `pending`, handoff `in-progress` unless you pass `status: "complete"` for finished work. Later transitions on older artifacts — `in-progress`, `complete`, `superseded` — are not publications; edit only that frontmatter line in place yourself, keeping its quoting. On actual supersession also add `superseded_by: "drift/<feature>/<successor>.md"` directly after `status`, using the exact path the successor's `drift_publish` reported, and nothing else. Do these edits only after the publications involved have succeeded — including any pending retry of the older artifact's own publication and of the successor's — because a retry verifies the published file is unchanged. Never guess or backfill a successor.

For a handoff, also pass `next_session_profile` (see "Profile-directed handoffs" in `SKILL.md`). The profile names the kind of receiving work, not a provider/model. Successful handoff publication completes only this thread's current interval; do not delete its record. A handoff published with `status: "complete"` has no open work: even with a profile and `autoContinue` enabled, nothing is queued.

## Profile-directed continuation

Continuation has exactly two modes. For a handoff whose work remains (`in-progress`), by default (auto-continue off) the handoff is only published: the tool result says nothing is queued; tell the user to run `/drift` (or `/drift <artifact path>`) to pick it up on their selected model when they choose, then stop. Where `.drift.json` sets `autoContinue: true` (`/drift-auto-continue on`), Pi starts a fresh context window from the handoff alone after `drift_publish` succeeds — no summary of this conversation and no transcript tail is carried; report that a fresh context window is queued and the profile/model the tool result names, and do not ask the user to run anything unless the automatic step fails. `/drift-auto-continue [on|off|status]` is a user command handled by the extension; suggest it rather than editing `.drift.json` yourself. In the fresh window, Pi uses its internal `drift-continue` step (not a user command) to validate the repository-local artifact, resolve its `next_session_profile` through the receiving machine's explicitly configured model map, select the mapped model and thinking level **before** inference, then follow the ordinary handoff workflow from the artifact's Next Steps. Missing/invalid profiles, unavailable models or failed authentication fail visibly without inference and leave the handoff intact; then suggest `/drift <published artifact path>` to pick it up on the user's selected model. See `docs/continuation.md` for the profile map format.

In `execute.md`'s long-running loop with `autoContinue` on this is the normal path: the next model reads the handoff and its referenced plan/research rather than receiving the old transcript.

To pick up an existing handoff manually, the user runs `/drift drift/<feature>/<NNN>-handoff-<description>.md`; it runs on the selected model, profiled or not. The automatic step refuses `complete` or `superseded` handoffs before switching models or starting inference, reports `superseded_by` when recorded, and never follows the successor automatically; use `/drift <path>` to request and explicitly confirm reopening.

## Session records

Before establishing the record, the extension prepares the session; it writes no derived file, never creates `drift/` and never edits `.gitignore`. In a linked worktree of a private repository it resolves the main worktree's `drift/` as the store and says so in context. Trust that store path and do not look for a `drift/` in the worktree.

The Pi extension establishes a durable record before work and supplies its path and measured baseline in model context. It uses Pi's actual session ID, not a model-generated manual ID. Records live under Pi's agent directory, separately from project artifacts and Pi's conversation logs, keyed to the launch repository; the record names the active Drift root and keeps history snapshots from earlier adoptions.

- Read **this thread's supplied record** when preparing an artifact. Its `started`, `startBranch`, `startCommit`, `baseline` and any `checkpoint` contain measurements, not a reconstruction from conversation memory. The publisher maps the original start into `session_started` and takes a fresh clock read for `date`.
- Records survive ordinary turns, reload, resume and compaction. Settled turns and teardown checkpoint observed changes; an ACP process detaching does not establish that the conversation is over.
- A successful `drift_publish` handoff completes only the current interval. The extension retains a receipt for retries so a retry cannot silently create a second handoff or reopen the same interval, and establishes a new measured interval on the next working prompt. Research and plan publication leave the current interval active.
- **Never delete Pi's session log or the extension's record.** Do not run retired manual hooks or substitute another thread's baseline. Publication failure must not be treated as completion.
- A Git diff can include inherited or overlapping work. Compare the recorded starting fingerprint and actual task history; do not claim everything in `git diff HEAD` as this session's work. Unreadable files have explicitly marked metadata-only fingerprints.
- A record is evidence about observed work, not proof that another thread is abandoned. Confirm ownership and the user's intent before using another thread's record for a reconstructed handoff. The publisher's frontmatter still identifies the current writing interval; do not substitute the other thread's ID or mark its record completed.
